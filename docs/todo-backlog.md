# 可做方向清单（按步骤累积）

> 规矩：每完成一步，回头问「它对体验有没有新启发」；有就记在这里，没有就写「无」。
> 一批做完再重新规划，不在半路改方向。

## R1 · 曲线三段依据 + 换耳机失效（0.9.35）

**这一步做到了什么**：每条记忆曲线现在带结构化三段依据（耳机 / 曲目 / 先验），耳机名对不上时界面标「依据失效」，并给「按当前耳机重调」入口。

### 启发 1：曲目依据是假的（高价值，依赖 iOS 频谱分析）

- 现在「曲目」段只有时长、采样率、专辑名 + 用户原话——这些不解释「为什么这首歌需要 +3 dB 低频」。
- 桌面已有 `analyze_track`（频谱画像：各频段能量、峰值、过零率），iOS 没有对应实现。
- 可做：iOS 侧离线分析曲目前 30 秒，产出「低频重心 / 高频滚降 / 动态」三数，写进依据；依据才配叫依据。
- 判定：做完后，用户能看到「这首低频本来就多，所以只抬了 1 dB」这类句子。

### 启发 2：失效的粒度太粗（中价值，依赖耳机目标曲线库）

- 现在只比名字：AirPods Pro → AirPods Max 会判失效，但用户不知道差多少。
- `ios/Resources/headphones-v1.json` 已有静态参数表；可做「差异估计」：把旧曲线套到新耳机目标上，算出偏差最大的 3 个频段，写进提示。
- 判定：提示从「依据失效」升级为「在 3 kHz 差了 4 dB，建议重调」。

### 启发 3：依据是「事后记录」，不是「事前生成」（高价值，指向自动适配）

- 当前曲线仍由人触发；依据只是记录。真正的自动适配应是：耳机 + 曲目 + 先验 → 直接生成曲线，再让用户改。
- 这是 R3/R4 的正题；R1 只把「记录」这一层铺好了。

### 启发 4：依据可以带走（中价值，与 Handoff 合流）

- 依据 + 曲线目前只在本机。`Handoff` 已能传数据，可升级为「传听感」：换设备后同样的依据仍然成立。

### 启发 5：先验需要版本号（低价值但会咬人）

- 依据里现在写「暂无校准」。R2 校准上线后，如果校准改了版本，旧曲线的依据会悄悄过期。
- 可做：依据里记「先验 v1」，校准更新时主动列出受影响曲线。

## R2 · 耳朵校准（0.9.36）

**这一步做到了什么**：四题 A/B（低频 / 人声 / 高频 / 齿音），选 B 的轴累加进 31 段先验（限幅 ±6 dB），带版本号与逐题选择记录；播放页可开关「叠加听感先验」，切歌回落与每首歌曲线都会叠加它。

### 启发 6：二值选择太粗（中价值）

- 每题只有「要 / 不要」，拿不到「要多少」。可做二分逼近：同一题两轮（+2 / +4），取用户偏好的档位。
- 判定：先验幅度出现 1.5 / 3 / 4.5 这类档位，而不是只有 0 或满值。

### 启发 7：先验应该按设备分（高价值，会咬人）

- 现在先验是全局一份：AirPods 上校准的 +3 dB 低频，换到监听耳机也照样叠加——那是错的。
- 可做：先把 `headphone` 作为键存多份先验，选中与当前路由匹配的那份；没有匹配就提示「这台设备还没校准」。

### 启发 8：叠加过程不可见（中价值）

- 现在是「基础曲线 + 先验」直接相加，用户看不到两段各贡献多少。
- 可做：摘要里展开成「链路 +3 / 先验 +2 = 最终 +5」，与 R1 的三段依据天然接上。

### 启发 9：校准素材不稳定（低价值但影响体验）

- 目前试听用的是正在播放的歌，切歌会打断校准。
- 可做：内置一段 20 秒校准素材（粉噪 + 扫频 + 人声片段），保证每次听的样本一致。

## R3 · agent 调音审计（0.9.37）

**这一步做到了什么**：一句话 → 2–3 条候选（AI 时）→ 挑一条应用 → 记一条审计（请求原文、来源、差异、改动前后曲线）→ 历史页可回到任一版本的前后状态。

### 启发 10：候选之间缺量化对比（中价值）

- 现在只有每条自己的差异行与一句 why，用户难以判断「候选 2 比 1 好在哪」。
- 可做：选中 2 号时额外显示「相对 1 号：低频 +2 dB、高频 −1 dB」。

### 启发 11：审计只在本机、只增不减（中价值）

- 记录上限 200 条，没有按曲/日期筛选，也不能导出。
- 可做：导出为 JSON（随加密备份走），或按歌曲过滤；跨端用 Handoff 带走。

### 启发 12：历史可以反哺校准（高价值）

- 如果用户连续多次都选「人声更靠前」，这就是一条比四题校准更真实的偏好证据。
- 可做：累计同类选择 ≥3 次时提示「要不要把这条写进先验（vN+1）」。

### 启发 13：回滚与歌曲记忆是两套状态（中价值，会咬人）

- 回滚只改当前播放曲线，不动 `songCurves`，用户会看到「历史回滚了，但下次切歌又变回去」。
- 可做：回滚时同步改/删这首歌的记忆，或在记录里标注当时的记忆版本。

### 启发 14：多候选需要「一键听差别」（低价值）

- 候选切换目前只换数字，用户要自己点应用才能听。
- 可做：候选卡片上直接「试听这条」（临时改线，不动记忆）。

## R4 · 跨端听感接力（0.9.38）

**这一步做到了什么**：iOS 把「校准先验 + 每首歌曲线 + 曲名」导出成一份 JSON（不含音频/凭据/历史），经 AirDrop / iCloud / 文件 App 传到桌面；桌面「导入听感档案」把先验叠加到当前曲线，并把档案留在 localStorage。

### 启发 15：桌面只有先验，没有按歌曲线（高价值，两端仍不对等）

- 档案里有 N 首按歌曲线，桌面只用了先验那一段；`songCurves` 在 Rust 侧根本不存在。
- 可做：桌面引入与 iOS 同构的 songCurves + 依据，导入档案时按歌落库；这样「同一副耳朵」才真的跨端。

### 启发 16：档案缺少「哪副耳机」的元信息（中价值）

- prior 只有 version 与 gains，没有 headphone 字段；导入方不知道这份先验是在什么设备上校准的。
- 可做：EarPrior 增加 headphone，导入时提示「来自 AirPods Pro，当前输出是 X，仍要叠加吗」。

### 启发 17：导入策略缺失（中价值，会重复叠加）

- 现在每次导入都直接相加；连点两次就会叠加两次。
- 可做：导入时给「替换 / 叠加」二选一，并记录已导入档案的哈希。

### 启发 18：档案版本没有迁移路径（低价值，早晚会遇到）

- `version: 1` 写死了，将来加字段（如按设备先验）需要 migration 规则与拒绝策略。

## v2 批次 · S1 桌面按歌曲线（0.9.39）

> **这一批就是 v2 的 S1–S4，不重排、不提前换方向。** 四个 S 的验收同时成立才算做完；
> 每个 S 收尾都回到这一节写「启发 N」——这是 loop 的唯一接口，不写就等于这一步没做完。
> 上一批（R1–R4）也是这么滚出 v2 的：每走一步问一次「它对体验有没有新启发」，有就记，没有就写「无」。

### S1 的真正难点：两端的歌 id 不通用

v2 里写的是「Rust 侧引入 songCurves」，但仓库里的实际情况是：

- iOS 的 `Song.id` 是 `UUID().uuidString`（`ios/Awake/Models.swift:7`）；
- 桌面用曲库 track id（`rust/crates/awake-core/src/models.rs` 的 `Track.id`）；
- 档案里唯一能跨端对上的是 `titles`（iOS id → 曲名），`ios/Awake/ListeningProfile.swift:13`。

所以 S1 不是「补一个字段」，而是**先解决键的映射**。同名多首时必须不猜、交回界面选——
错配的曲线比没配上更难发现。

### 拆成三个子步

| 子步 | 做什么 | 验收（可跑） | 状态 |
| --- | --- | --- | --- |
| S1-a | 纯逻辑：档案解析、31 段校验、曲名归一化匹配、先验叠加 | `cargo test --manifest-path rust/Cargo.toml -p awake-core listening` → 9 项 | ✅ 2026-11-23 |
| S1-b | 桌面落库 + 命令：`song_curves.json`、`import_listening_profile`、按曲查询、切歌自动套用 | 导入一份真档案后，切到同一首歌，`playback_status` 的曲线与档案一致 | ✅ 2026-11-23（6 项测试） |
| S1-c | 播放页三段依据 + 「记住这首歌」+ 未匹配清单（同名/找不到分开说） | 桌面播放页能看到「耳机 / 曲目 / 先验」三段，且失效时写明差在哪 | ✅ 2026-11-23（8 项测试 + 打包） |

**S1-a 已落地**（2026-11-23）：

- 新文件 `rust/crates/awake-core/src/listening.rs`，纯逻辑、无文件与 Tauri 依赖；
- 9 项断言：camelCase 档案解析、未知版本拒绝、坏曲线跳过但保留其余、空档案报错、
  曲名归一化匹配、同名多首判歧义、缺曲名/找不到分开报、先验先加后限幅 ±12；
- 一条被删掉的假测试值得记下来：本想用 JSON 里的 `NaN` 触发「非法数值」分支，
  但 `serde_json` 直接拒绝（`number out of range`）——**那条分支从 JSON 永远进不来**，
  改成直接断言数组边界的防御，才不是自欺。

**S1-b 已落地**（2026-11-23）：`rust/crates/awake-app/src/song_curves.rs` + `ui/src/useAwake.ts` + `ui/src/App.vue`

- `song_curves.json` 落库（原子写；坏文件留 `song-curves-corrupt-<ms>.json` 再从空库起步）；
- `import_listening_profile`：解析 → 按曲名落到本地 track id → **不动当前播放曲线**；
- `curve_for_track`：切歌时算「这首歌该用什么」；`remember_song_curve` / `forget_song_curve` / `song_curves_summary`；
- 前端：`start()` 里先问一句再播；导入后若正在播的那首命中就立刻套用；
- 6 项断言：指纹形态、设备名容错、段数校验、落库往返 + 坏文件留副本、档案→匹配→叠先验→限幅的整条链。

**S1-b 没验证到的**：GUI 里的点击路径（选文件 → 切歌）。逻辑、类型检查、打包都过了，
但「手点一遍」在这里做不了——这正是 v2 说的结构性缺口；S2 的自检只锁得住纯函数，锁不住手势。
所以这一格写「✅ 测试与打包」，不写「✅ 已听」。

**顺带发现（不属于 S1，别丢）**：`backup.rs` 的备份/恢复只搬 `library.json` 与 `taste.json`
（`backup.rs:380`），`song_curves.json` 不在里面。换机恢复后按歌记忆会整份消失。
与 R4 启发 11「审计导出不全」是同一类问题，下一批一起处理。

### 启发位（每完成一个子步回来写）

- 启发 19（S1-a）：**验收要能失败，才叫验收。** 原打算用 JSON 里的 `NaN` 触发非法值分支，
  结果 `serde_json` 直接拒绝——那条分支从 JSON 永远进不来。改成直接断言数组边界后，
  这条测试才真的能红。同理，S2 的自检项每一条都要先能红。
- 启发 20（S1-b）：**把「导入」和「生效」拆开，比加一个确认弹窗更能防重复叠加。**
  旧实现导入即改当前曲线，所以连点两次就叠两次；现在导入只落库，生效在切歌时发生，
  重复导入只是覆盖同一份数据。结构上不可能叠两次，就不需要提醒用户「别再点了」。
**S1-c 已落地**（2026-11-23）：`ui/src/CurveBasisCard.vue` + `ui/src/curve.ts` + 后端三个 pending 命令

- 「声音」页 EQ 区新增「这首歌的依据」卡片（桌面调音与曲线都在这一页，放在这里才跟操作在同一处；
  底部播放条空间不够，不塞）：三段依据逐条写出，缺哪段写「未记录」；
- 依据失效时写清「记的是哪副耳机 / 现在用的是哪副」，并给「用当前曲线更新记忆」；
- 「记住这首歌」把当前曲线 + 三段依据一起写回（耳机取当前输出，曲目取时长/采样率/专辑指纹）；
- 导入时落不下来的曲线进 `pending`，卡片列出待指定清单，候选可点：
  **精确同名在前，「夜航」↔「夜航 (Live)」这类包含关系接在后**，一次点击能看到所有可能；
- 找不到近似曲目时明说「先在桌面导入这首歌」，不假装有候选；
- 版本 0.9.39（四处同步：Cargo / package.json / version.ts / tauri.conf.json）。

**S1 三个子步到此都落地了。** 但 v2 那条整体验收还差一次人工：
「在 iOS 调一首歌 → 导出档案 → 桌面导入 → 播放同一首歌，曲线与依据都在；换一首没记忆的歌，回落链路曲线」
——代码路径通了、逻辑与打包都验了，可「真机上点一遍」在这里做不了。没点过就不写「已验收」。

- 启发 21（S1-c）：**「不猜」需要一个出口，否则等于没做。**
  同名多首时不自动选是对的，但如果只报「同名 2 首」而不给可点的候选，
  用户就得自己去曲库翻——那不叫不猜，那叫把活推回去。所以 pending 必须带候选。
  另一头：候选的宽松匹配（包含关系）不能替用户决定，只能排在精确之后。
  这一条对 S2 的自检同样适用：报红不算完，得指出「哪一项、差多少」。
