# 下一批规划（v2）：把「知道我的耳朵」做成双向成立

> 依据：R1–R4 四个版本 + 18 条复盘方向（见 `todo-backlog.md`）。
> 这一批只做四件事，其余明确冻结；每版都要有一个「能听或能跑」的验收。

## 一、上一批证明了什么、没证明什么

**证明了（结构层）**：

- 一条完整链存在：依据（R1）→ 先验（R2）→ 可审计自动调（R3）→ 跨设备带走（R4）。
- 每一步都能在代码里定位到具体字段与动作，不是概念。

**没证明（运行层）**：

- iOS 没有可跑的 XCTest；桌面 GUI 无法在开发环境点击。四个版本的验收基本停在「ARCHIVE SUCCEEDED + 包内字符串」。
- 一次性字符串核对还出现过异常（「回到改动前」未在二进制中找到），说明这套验收本身不可靠。

**两个结构性缺口**：

- 桌面只接力了先验，没有按歌曲线（18 条里的第 15 条）。
- 先验是全局一份，换设备仍叠加（第 7 条）——这不是缺功能，是**算错**。

## 二、18 条聚类（决定优先级，而不是逐条排）

| 簇 | 包含 | 一句话问题 |
| --- | --- | --- |
| A 依据要真 | 1、2、4、16 | 「曲目」段只有时长采样率，失效只知道「不一样」，不知道差多少 |
| B 先验要对 | 6、7、9、12 | 先验不分设备、只有二值选择、不随历史进化 |
| C 改动可追 | 10、11、13、14、17、5、18 | 候选不可比、审计不能导出、回滚与记忆脱节、导入会重复叠加 |
| D 两端对等与可验证 | 15、3、8 + 自检缺失 | 桌面缺一半能力；所有结论都缺运行时证据 |

## 三、这一批：S1–S4

### S1 桌面按歌曲线（对齐 R1–R3 的数据与交互）

- 目标：桌面上每首歌也有曲线、依据、先验叠加；导入听感档案时**按歌落库**，不再只用先验。
- 为什么现在：两端不对等是最大裂缝，「同一副耳朵」在桌面目前只成立一半。
- 范围：Rust 侧引入 `songCurves`（与 iOS 同构的字段）、`basisDetail`、先验叠加；Vue 侧播放页显示三段依据与「记住这首歌」。
- 验收：在 iOS 调一首歌 → 导出档案 → 桌面导入 → 播放同一首歌，曲线与依据都在；换一首没记忆的歌，回落链路曲线。
- 粗估：1.5 天。

### S2 可验证性：两端自检（替换「编译通过」式验收）

- 目标：把纯逻辑（曲线限幅、差异文案、依据失效判定、档案解析、先验叠加）做成**设备内可跑**的自检清单。
- 为什么现在：在补更多逻辑之前先给已有逻辑上锁；否则 S1/S3 只会把不可验证的面积扩大。
- 范围：iOS「诊断 → 自检」页（Swift 纯函数断言，逐条 PASS/FAIL）；桌面同构的命令 `self_check` 返回清单。
- 验收：故意改坏一个常量，自检页对应项变红；恢复后变绿。**这一条本身就是验收**。
- 粗估：1 天。

### S3 先验按设备分组 + 导入策略（修正确性，顺手补策略）

- 目标：先验按耳机/输出设备分开存；导入档案时给「替换 / 叠加」二选一，并记录来源耳机与已导入哈希。
- 为什么现在：全局先验会算错；导入重复叠加也是算错。两者同属「正确性」，一次修完。
- 范围：`EarPrior` 增加 `headphone` 与按设备字典；校准页写入当前设备；播放叠加时按当前路由选先验；导入弹窗二选一。
- 验收：在两副耳机上各校准一次 → 切换设备时先验跟着换，且界面写明「当前用 AirPods Pro 的先验 v2」。
- 粗估：0.5–1 天。

### S4 频谱依据（让「曲目」这段第一次有数据）

- 目标：iOS 离线分析曲目前 30 秒，产出低频重心 / 高频滚降 / 动态三个数，写进 R1 的「曲目」段；失效提示升级为「差异估计」。
- 为什么现在：A 簇里最能让定位站住的一条；而且不需要新服务，只吃本地数据。
- 范围：复用 `decode` 的能力做一次性离线分析（缓存结果，按文件 mtime 失效）；依据文案从「3:42 · 48 kHz」升级为「低频偏多，所以只抬 1 dB」。
- 验收：同一首歌的摘要能说出「这首本身低频就多」，且与曲线方向一致；换一首低频少的歌，文案随之变化。
- 粗估：1.5–2 天。

## 四、本批明确不做（写清楚，免得被当成遗漏）

- 校准 2.0（二分逼近、内置素材）：先验的正确性比精度更重要，放下一批。
- 候选量化对比、候选试听：属于打磨，等 S1 把两端拉平后统一做。
- 审计导出、回滚联动记忆：与 S3 的「导入策略」同属状态一致性，下一批一起处理。
- 不做任何新来源、不做插件扩张、不做 UI 大改：这一批只允许「让已有能力变真」。

## 五、风险与自我反驳

- **S1 可能比预估大**：Rust 侧没有 `songCurves`，等于把 iOS 的模型搬一遍；如果 Rust 库结构不合适，先做最小字段（gains + basisDetail）再谈交互。
- **S2 的自检不能替代 UI 验证**：它只锁纯函数，界面与手势仍要人点。这一条要写在自检页顶部，不能让人误以为「全绿 = 产品可用」。
- **S4 的频谱分析可能拖慢首播**：必须异步 + 缓存 + 失败即跳过，绝不能在播放路径上同步分析。
- **最坏情况**：四版做完，用户仍说不出「它知道我的耳朵」——那说明问题不在能力而在表达，下一批应该做「让用户自己发现」而不是再堆能力。

## 六、这批做完怎么判定

1. 在桌面上播放一首在 iOS 调过的歌，曲线与依据都在（S1）。
2. 故意改坏一个常量，自检页变红（S2）。
3. 换一副耳机，先验跟着换且写明来源（S3）。
4. 摘要能说出「这首低频偏多」（S4）。

四条同时成立，才叫「这一批做完了」；只完成三条也算未完成。
